# Stage 2 1.1.2：操作、证据、条件与预算修正

范围仍为前三批，公共输出保持 v0.4；不实现 Stage 3/4，不把预期答案或漏洞报告提供给 Agent。分析器与 API 同步升级为 `authz-java-1.1.2`，旧任务可读取，旧版本检查点不能用于新版本继续任务。

## 修正

- 操作导航增加调用偏移、资源及动作事实。不同资源或增删效果不能共用一个宽泛锚点；多操作检查显式关联目标操作，不猜测关联，不默默丢弃指向辅助操作的引用。已读写效果若没有主操作或有依据的辅助操作关联，强制保留未知。SQL 映射的自定义写方法也进入候选，不仅识别 CRUD 名称。
- Agent 提交工具内部要求 `operation_refs`；公共结果仍使用既有 `operation_ids`。拒绝提交时返回具体原因及可用引用，最多允许一次修正，保留每次拒绝记录，不自动放宽校验。
- CST 提供条件、return/throw、catch 和写操作位置。资源关系检查必须引用比较及拒绝语句，只有 owner 查询或后续写入的证据不能通过；源码明确后置的检查拒绝，存在 catch 而传播未证明的检查降为候选。仅有 SQL 范围应使用 query_scope 及可信来源绑定。
- Shiro 路由保留精确声明；JWT 正式条件中不存在于源码的通配模式被降为待核查，不以同目录路由推导 `/sys/**`。这是一项有界的通配声明核查，不是完整自然语言语义验证。
- Mapper 的 InterceptorIgnore 通过 namespace/statement 与声明方法关联，覆盖没有方法体的接口。必须有源码支持的解释记录，否则保留明确未知；不会因为读过注解就宣称已经解释。
- 反射字段赋值附带 INSERT/UPDATE、字段匹配、空值等全部包围条件。辅助赋值描述归一为这些条件事实，原始模型概括只留在审计中，不能把空值填充直接当成无条件覆盖。
- 重复源码范围和安全上下文读取返回已读提示，减少重复内容；未解析调用分组分页缩小。关键调用仍必须有处理依据，不为获得 completed 清除未知。具体部署值、单个用户权限值等可通过已有 deferred/conditional 记录解释。
- 每次模型请求前检查轮次、工具、用量及下一次调用预留，SDK 提前拒绝工具参数也不能绕过限制。预留考虑上次实际输入（含缓存）、输出、上下文 UTF-8 增量与最大输出，预算不足时保留检查点并明确停止。它不是精确 tokenizer 或供应商硬计费上限；实际用量以 SDK 为准，不增加原预算。

## 验证记录

- Docker Worker：58 项测试通过（含原有 Stage 1/2 回归、真实 Pi SDK 的本地协议 fixture）；TypeScript 类型检查通过。

- Web Docker 生产构建通过；详情页面可查看条件事实、资源效果关联、机制解释及辅助操作。
- 对固定 JeecgBoot 快照的程序核查能定位 N5 的关系增删、退出租户的不同资源删除、角色列表 Mapper 忽略设置。程序索引核查不等于模型语义验收。
- 历史结果、真实模型、生命周期与部署核查在独立验收记录中更新。此处规则和 fixture 通过不能替代真实模型成绩。

## 支持边界

这不是完整控制流证明或任意自然语言的真实性校验。跨方法拒绝传播、catch 中重新抛出、复杂代理、反射、动态 SQL 与多实现仍可能需要保留未知。操作被标为辅助是否符合业务含义、主体和资源绑定是否正确，仍需真实样本复核。找不到授权要求时不得反向补造规则；本版本仅恢复实际实现。

## 1.1.2 真实任务暴露的回归与 1.1.3 修正

1.1.2 冻结提交 f4712e2 的真实重验在前三项后停止：三项均因预算预留终止，共 65,929 Token。前两项把 UTF-8 增量当作 Token，过早阻止首个后续请求；第三项还暴露 SDK 参数错误会回显整份提交、增加下一轮上下文。原清单、首次失败、当前任务采集记录及停止原因均保留，不能称为十八项验收通过。

1.1.3 改用文本 Token 规划估算，并根据上一轮供应商实际输入校准，增加 25% 增量余量；仍预留完整输出，不增加预算，不声称精确 Token 上限。SDK 错误反馈给模型时只保留具体错误，原始重复参数仍保留在审计转录中。初始字段上下文只提供名称、位置、类型及说明，完整字段证据仍可按需查询；不修改冻结字段或引用。移除初始资源关系导航里无关的审计拦截器条件，但赋值事实保留全部条件。

增加连续两项预留失败停止后续收费提交的保护。必须另建 1.1.3 清单、固定代码及镜像，不能修改 1.1.2 失败任务或复用其检查点。1.1.3 Docker Worker 测试 60 项通过，PostgreSQL 回归 20 项通过；真实成绩见后续独立验收报告。

## 1.1.5：来源分类、辅助关联与更小的模型核心

1.1.4 运行八项后停止，四项正常结束、四项失败（343,057 Token），见 [独立记录](acceptance-hardening-v114.md)。它不满足验收门槛。

- 最终工具只接受 authentication/action_permission/resource_relation/query_scope。验证前提、普通筛选和观察通过审计笔记的 checks 记录；最终结果仍沿用原公共格式。精简系统指令，避免同时要求将辅助说明既放笔记又放核心检查。
- 一个检查显式关联主操作与辅助查询时，核心结果只关联其明确指定的主操作，辅助关联完整保存在 supporting_check_relations；只引用辅助或不存在的操作仍被拒绝，不猜测受保护的主操作。
- database_policy 必须有已定位的策略加载/消费机制；仅数据库原值、旧 owner 或更新定位条件不能成为正式策略检查。无法证明时保留候选和未知，不反推预期规则。
- 调用组概览最多展示每组六个组的三个调用，详细页每次十二个，明确 total_calls/next_call_offset；完整调用台账及关键未知保留，不以分页隐藏未解析项。
- 用实际测量校准上下文估算时允许向下校准估得过高的文本，保留 25% 增量余量和完整输出预留。仍为规划估算，不是计费硬上限；预算不增加。
- Docker Worker 64 项规则/SDK fixture 回归通过。另以历史 N1/角色编辑提交做程序重放：有效核心可保存，原值伪策略被扣留，辅助关联有独立记录。重放不是新模型验收，不替换历史首次失败。

## 1.1.6：有界源码包与实际未读范围

1.1.5 首次十项中八个对照通过，N1/N5 仍在大上下文往返中无法及时提交。费用及失败见 [独立记录](acceptance-hardening-v115.md)。不改变原单任务预算。

- get_analysis_bundle 一次真实工具调用读取入口、至多六个两层内方法（各至多 120 行）、至多八个 SQL 及直接 include、Mapper 声明与 @Param，以及适用安全机制。单段源码仍最多 100 行，长方法/SQL 截断及剩余调用不隐去。鼓励下一回复提交核心；缺少关键源码仍可定点补查。工具不包含预期答案。
- 已定位但未完整阅读的方法和 SQL 形成 unread_methods/unread_sql 详情与程序强制未知；不再把“索引找到方法”当作已经分析。相关 SQL 不完整时，涉及其范围/关系的检查不能成为已确认保护。
- 失败后的范围审计按实际读取重新计算，移除初始未读标记的旧副本、保留当前真实未知，不将程序初始状态误写为最终未读事实。
- 会话内重复读取去重与历史检查点读取范围分开。继续任务的新会话仍能重新取得源码内容，不能因为旧任务曾经读过就只返回“已读”。笔记与最终提交在同一回复出现时按顺序执行。
- 检查 ID 包含字段、条件、绑定和操作关联，相同谓词分别保护不同操作时不会错误触发重复 ID；完全重复检查仍被拒绝。
- 补充权限代理 creator 的前缀条件与 AOP 依赖声明阅读；注解型检查必须表达代理适用条件，直接 checkPermission 调用另行区分。一个 creator 的排除前缀不等于所有 AOP 关闭，不据静态声明假定部署已启用。参考 [Shiro Spring 集成](https://shiro.apache.org/spring-xml.html)、[Spring Boot AOP 条件](https://docs.spring.io/spring-boot/reference/features/aop.html)。
- 明确保留 TARGET 与目标资源的真实成员关系约束，不将其改写为请求者 owner 校验；纯存在性、格式和普通过滤仍单列说明，不反向推断授权要求。
- Docker Worker 67 项规则/SDK fixture 回归通过，含两回复源码包、继续任务重新提供源码、顺序笔记、未读范围和代理适用条件。真实模型效果仍须以新的固定清单核对，不与 fixture 混算。
