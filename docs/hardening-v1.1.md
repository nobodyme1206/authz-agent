# 前三批补齐与统一重新验收

本轮只补齐基础环境、Stage 1 与 Stage 2，不实现 Requirement 推断和漏洞比较。继续使用公共格式 v0.4，不增加核心必填字段，不创建业务表。历史任务、结果和首次失败不可覆盖。

## 实现变化

Stage 2 分析器升级为 authz-java-1.1.0。历史 1.0.0 结果可读取，但不能作为新版本继续任务的基础。

- 必须核查的机制按关键方法、匹配路由、适用表、配置分支及数据权限消费链记录源码范围，不再用同文件任意一行代替完整核查。
- 外部 excludeUrls 等配置适用条件进入内部 obligations。缺少 JWT 路由适用条件的提交不会成为有效检查；检查被降为候选，并强制保留未知。已知 false 分支不得成为有效保护。
- 每条实际检查由 Agent 提交执行效果及已读的拒绝/SQL/代理证据。未阻止操作的内容只在详情保存；效果未知时降为候选并保留未知。程序提供分支、顺序和引用事实，没有实现完整控制流证明。
- 调用以源码入口、位置及参数生成稳定引用；按声明类型归类标准库/框架边界。未解析的自定义调用必须保留为未知，或提供覆盖全部调用点的源码依据和处理理由。已定位调用不自动代表检查生效。
- 主操作以业务资源效果为单位。辅助查询、分页、日志等保存到详情；相同资源、动作、源码锚点的重复描述合并。多操作检查必须显式引用受保护操作。不同锚点是否实际同一动作仍需语义复核。
- 特定用户实际获授哪些权限、某行当前取值等不总是谓词提取的前提。可用有依据的处理记录区分阻断未知、配置条件和延后事项；程序强制保留的关键未知不能批量清除。
- 内部审计内容保存到既有 JSON 详情，包括 mechanisms、call_groups、supporting_operations、unconfirmed_checks、unknown_reviews、mandatory_unresolved。页面可查看这些记录及执行版本，不增加 Agent 公共输出负担。

位置、阅读和结构校验仅证明引用存在，不能证明语义正确。调用分组的框架归类也不意味着已经证明 SQL 谓词或拦截器保护。类名可混淆、复杂代理、反射及缺少依赖仍需保留边界。

## Stage 1 边界

Stage 1 仍为 spring-java-1.0.5；本轮未改变确定性提取行为及 API 编号规则。重新提取时使用相同固定 JeecgBoot 快照、enrich=false，不进行全量收费补全。比较原有 20 个 API/81 个字段与全部 API 标识。对 91 个疑难 API 分类抽查；不以清零未知为目标。

Pi 可以细化已有绑定、类型和说明，但不能仅声明 resolved 就删除确定性诊断。无可证明的跨文件/深层/嵌套新增字段保守拒绝。新增回归测试覆盖跨两层 helper 限制和嵌套动态字段拒绝；这些能力限制不能冒充完整对象恢复。

## 冻结后的真实模型验收

用 `scripts/hardening-acceptance.py prepare artifacts/hardening-v110-manifest.json` 固定源码、18 个 API 输入哈希、代码提交、镜像、生产源码哈希、提示词哈希、锁文件、模型和部署预算。prepare 只创建两个确定性 Stage 1 任务。源码语义对照只导出 evaluation/control-sources 内的 Java 源码；人工预期文件不进入源码快照和模型上下文。十个真实接口预期也只供独立复核。

冻结前运行 Docker 构建、单元测试及 PostgreSQL 回归，提交实现后用 `docker compose build --build-arg BUILD_COMMIT=$(git rev-parse HEAD) agent-worker` 构建 Worker 并更新空闲服务。`execute` 每项最多创建一次 Stage 2 任务；提交前保存意图，响应丢失后不得自动重复提交。任务首次结果、失败、未知和用量分别保留，不能挑选成功任务替换失败。

18 项包括十个已参与开发的 JeecgBoot 回归接口和八个中性最小源码对照。对照分别检查可信 SQL 范围、拒绝顺序、异常是否被捕获、配置真假。它们的预期在执行前固定，但仍属于已知设计的语义验收，不宣称盲测或泛化结果。

每任务 60,000 Token、12 轮、30 次工具、180 秒模型时间、300 秒总任务时间。18 项名义合计 1,080,000 Token，单个在途请求可能略超。收费请求不自动重试；失败和预算中断不隐藏为成功。测试 fixture 使用本地 HTTP 模型响应，只验证 Pi SDK/协议行为，不等同于真实模型效果。

所有验收采用 Docker、自动化测试、HTTP 和容器检查，不用截图或浏览器点击。最终报告必须区分通过、失败、未执行。八个完整源码对照存在关键语义错误或关键未知即未通过；真实接口允许有具体依据的 partial，但不得含关键主体/范围/执行效果错误。未满足门槛时暂缓批次四。
