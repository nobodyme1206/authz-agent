# 最终 case 评估规范

本文件建立后续完整工具评估的规范，本轮不运行 Stage 3—4，不填写漏洞检测结论。评估记录独立于 Agent v0.4 核心输出。

每个样本保存固定源码与工具版本、运行标识、人工依据、工具结果、首次失败、预算和复核理由。分类如下：

| 分类 | 判定依据 |
|---|---|
| 有依据的发现 | Requirement、实际实现、差异和适用范围均有源码依据；运行复现另外记录 |
| 漏报 | 人工找到充分的授权依据及差异，但工具未找到；记录发生在哪一阶段 |
| 误报 | 候选的政策、实现差异或可达前提经复核不成立 |
| 证据不足 | 现有源码/配置不足以判断，不能当作安全或漏报定论 |
| 方法覆盖边界 | 人工复核相关前后端流程和其他合法工作流后，确认缺少足够的 Requirement 来源；写明已检查范围 |
| 执行失败或中断 | 记录模型、工具、预算和任务故障；不归入成功或安全 |

`requirements: []` 不表示安全，也不直接证明方法无法覆盖。人工能找到充分 Requirement 而工具没有提取出来，属于能力缺口。只有复核相关流程、适用条件和证据后才能确认方法边界。

漏洞报告只可作为人工选样/事后比较材料，不能成为 Agent 输入，不能从已知漏洞反向补造授权规则。不得为了命中某个 case 修改事实。原有比较枚举不变，以上分类仅保存在独立评估报告。

JeecgBoot N1/N3/N5 等已参与开发调试，必须标注为已知基准回归，不能宣称严格盲测。泛化能力需要另行固定未参与调参的样本及首次运行协议。发现语义错误后保留原批次；修正后的收费重验须另建批次，不能替换首次结果。
