## 结论

目前不能宣布批次三验收完成。已确认的问题分为接入、提交协议、语义和验收四层。四阶段研究方法没有因此被证伪；Stage 2 的实际实现尚未达到作为下游可靠输入的标准。也没有证据表明更换 Pi、引入 LangGraph 或单纯增加 Token 就能解决这些问题。

### 1. 接入层存在真实工程错误

| 问题 | 实际证据 | 处理与边界 |
| --- | --- | --- |
| 上下文压缩丢失系统消息及工具声明 | 1.1.10 的最终请求工具数为 0 | 后续使用 SDK 的 getCurrentSystemMessage 保留当前规则和工具增删状态；不能只保留用户消息 |
| 配置输出 4096，不代表实际请求始终为 4096 | 安装版 SDK 根据剩余上下文减去安全余量后裁剪 maxTokens；旧请求曾只剩约 1666 输出额度 | 按 SDK 估算保留输出空间，并记录真实 provider payload；估算不等于精确计费 Token |
| Pi thinkingLevel=off 未映射成 DeepSeek 的关闭参数 | 1.1.12 两次长度截断，output=4096，其中 reasoning=2643/2667 | 1.1.13 对官方端点显式发送 thinking.type=disabled；该轮 reasoning 实测为 0。关闭思考只是接入修复，不等于证明此模式的分析质量足够 |
| 强制工具选择与当时的供应商思考模式不兼容 | 1.1.11 返回 Thinking mode does not support this tool_choice | 已撤销 required；不把普通文本当作正式工具提交 |
| SDK 参数校验发生在工具 execute 之前 | 截断参数没有进入原本写在 execute 中的修正逻辑 | 后续捕获 SDK 工具拒绝事件，仍限制最多一次修正，不能隐式重试收费调用 |

这些不是被测 JeecgBoot 的问题。其中工具丢失及额外强制工具选择是修复过程中引入的回归，应由实现承担责任。

### 2. 提交协议仍把过多工作压到一次输出

Agent 同时负责查源码、理解授权、拆分操作、填写字段引用、选择证据类型和生成较大的嵌套 JSON。原始位置与 proof ID 并存，操作锚点与普通已读范围又有不同资格。即使接入已经修正，仍有缺少执行效果证据、选择错误锚点等失败。

不能用放宽正式证据要求来解决。应保留已验证的操作，把证据不足的检查留作候选和核心未知；这类样本在独立语义验收中仍属未通过，不能用 partial 标签掩盖提取失败。

后续改造应优先在内部工具协议进行：按操作保存小份分析成果，再关联检查；由程序分配编号、解析证据和包装公共结果。源码阅读台账、模型当前可见原文、证据引用必须保持一致。探索与正式提交分离，但不能规定第二轮必须提交，也不能要求用户手动继续才能补读关键源码。以上不需要增加公共核心必填字段。

### 3. 成功提交后仍有授权语义错误

1.1.13 的 N5 正式结果把 Advisor 前缀不匹配表述为权限检查生效。Spring 的真实规则是：启用前缀筛选时，只有匹配前缀的 Advisor 才有资格被该 creator 使用。单个 creator 排除某 Advisor，也不能推出整个系统所有代理均关闭。

这类错误不能靠 JSON Schema、行号存在或“读过文件”检验消除。程序适合提供声明、比较、值来源、调用、分支和操作事实；模型负责结合上下文解释。对于能确定的反向解释，程序应拒绝把它作为正式保护；对于尚未确认的代理链，应如实保留未知，而不是编造“有效”或“无效”的部署结论。

本次审查还发现未提交防护里的类型识别过宽：包含 Advisor 的字符串会误收 AutoProxyCreator，匹配的无关 Advisor 也可能遮蔽 Shiro Advisor 不匹配。现已收窄为已声明 Bean 的 Shiro Advisor 类型或源码可解析的子类，并增加中性测试。其结果仅表示声明的代理资格，不证明运行期代理实际应用。Shiro 的事实也不能直接用来判断 Spring Security 的 PreAuthorize。

### 4. 旧测试没有充分覆盖真实请求契约和语义

早期模拟供应商能够返回请求中未声明的工具，所以即使真实请求没有工具，模拟测试仍可能成功。规则 fixture、供应商协议 fixture、历史提交回放和真实模型验收必须分别记录，不能互相替代。

后续门槛应是：先检查真实 SDK 序列化后的请求是否保留系统规则、工具声明和输出空间，再测试 length、错误参数及拒绝修正；最后才用固定模型运行语义样本。语义验收仍要求独立源码复核，不能仅靠校验器自己给自己的输出判正确。

## 本次免费修复与后续顺序

本次保留并审查未提交的 1.1.14 修改：缺失执行效果证据时保留有效操作，但撤下无法确认的检查并保留未知；补齐 Advisor 类型、Bean、继承及无关 Advisor 的对照。没有修改历史结果，也没有据此宣布模型验收通过。

本次 Docker 检查：Worker 80/80、TypeScript 类型检查、API 20/20、隔离 PostgreSQL 20/20 均通过；运行环境检查通过（四服务健康、仅回环 Web 端口、非 root、只读及挂载/密钥检查）。这些是程序回归记录，不是 1.1.14 的真实模型验收。实际收费模型记录仍停留在上述 1.1.13 轮次。API 测试有一条现有 Starlette/httpx 弃用警告，不影响本轮通过。

下一步按以下顺序推进，避免再次以整轮收费试错来发现基础接入错误：

1. 固化已确认的 SDK/供应商请求契约回归，模拟端必须拒绝未声明工具；保留原始失败与实际请求元数据。
2. 整理小份提交与证据引用协议，用历史失败和中性源码测试执行效果、条件、操作粒度及候选保存；不降低正式结论证据标准。
3. 免费回放既有提交，明确“协议可接受”与“语义正确”的差别；开发样本修复不能宣称泛化通过。
4. 冻结新版本后再开展独立收费复验；新的付费批次需单独记录预算和首次成绩。目前没有完成该项。
5. 只有十个真实接口和八个语义对照达到既定门槛，才进入批次四。

不直接启用 DeepSeek strict Beta：其官方文档要求 Beta 端点、每个对象所有属性 required、additionalProperties=false，且支持的 Schema 子集受限。当前工具存在大量可选属性，不能只加 strict=true；即使适配完成，也只能约束结构，无法证明授权语义。是否采用应在小协议改造后单独评估。
