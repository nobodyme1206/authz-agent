- 程序填写任务元数据，Agent 重点输出分析内容。
- Stage 1 批量提取 API；Stage 2—4 按 API 分批分析。
- 授权规则首先使用明确的文字描述，不强制生成复杂表达式。
- 源码证据、关键条件和不确定性必须保留。
- 映射、传播路径和多操作关联，只在影响判断时展开。
- Web 平台、后端、Agent Worker 和数据库在 Docker 中运行，依赖安装与分析执行不污染宿主机环境。

比较实际检查与预期要求，输出覆盖结论或疑似授权缺口。

2. 比较实际检查是否等价于或强于预期要求。
3. 核对配置、管理员例外、AND／OR 和执行分支。
4. 确认相关字段确实影响实际资源操作。
5. 检查前面阶段的未解决问题是否影响当前结论。
6. 输出结果、理由和必要的补查任务。

运行验证结果由平台单独管理，不与静态覆盖结果混为一谈。首版四阶段默认进行静态源码分析，不自动部署被测系统或执行漏洞请求。

- 检查与要求约束相同资源和操作。
- 不遗漏 SQL 或统一机制的等价保护。
- 不因关键路径未解析就直接报告漏洞。
- 不因未提取到要求就判断安全。
初版不强制输出复杂 predicate 或 constraint，但 rule 必须表达清楚：
```text
主体：谁发起操作，谁是目标用户
资源：操作哪条数据或哪类关系
条件：需要满足什么关系或权限
场景：在哪些情况下成立
```
示例：
```text
不够明确：
用户必须属于租户。

明确：
请求中userId对应的目标用户，必须属于tenantId对应的租户。
```
```text
不够明确：
roleCode不能修改。

明确：
编辑已有角色时，提交的roleCode应与数据库中原roleCode保持一致。
```
N1 的 record.username === record.createBy 首先表示两个行数据属性相等，不能未经来源追溯就归一化成“当前请求者是 owner”。
如果评估发现自然语言比较持续产生歧义，再为高频规则增加轻量结构化条件，不提前要求所有案例使用统一表达式树。
采用 Pi 作为 Agent 运行底座。Pi 按阶段和 API 调用源码工具，分批保存检查、要求和比较结果。四个 Stage 是工作阶段，不要求实现成四个独立 Agent。
程序负责：
- 路由、字段等可确定信息的提取。
- ID 分配和引用校验。
- 源码路径、行号与版本校验。
- 结果保存、失败恢复和前端展示。
- 按需向 Agent 提供相关上下文。
Agent 负责：
- 决定需要继续查看和追踪的相关代码。
- 理解授权检查的主体、对象与业务含义。
- 提取要求并补齐关键传播证据。
- 比较要求与实现，提出候选缺口和补查任务。
Stage 2 与 Stage 3 均依赖 Stage 1 的 API 入口信息，逻辑上可以分别开展。对比时读取两者结果；遇到关键未知，回到对应阶段补证据，而不是重新扫描全部项目。
